# 让导航栏逻辑学习 blog.moewah.com

## 关键发现

参考站 **本身就是 Firefly 博客**（同样有 `float-panel`、`dropdown-container`/`data-dropdown`、`semifull` 滚动逻辑、完全相同的键盘导航 `<script>`）。所以差异不是"换一套实现"，而是**数据组织 + 少数行为细节**。

对比结果：

| 维度 | 参考站 moewah | 当前 Firefly |
|---|---|---|
| 顶层结构 | 扁平：主页 / 专题 / 归档 / 周刊 / 友链 / 留言 / 关于▾（**仅 1 个下拉**） | 分组：主页 / 文章▾ / 社交▾ / 我的▾ / 关于▾ / 链接▾（**5 个下拉**） |
| 叶子链接 | 也用 `dropdown-container` 包裹、复用同一 `DropdownMenu.astro` | 同 |
| 下拉显隐 | `visibility+opacity+translate-y` 全在 `.dropdown-menu` | `pointer-events` 在 `.dropdown-menu`，`opacity/translate` 在 `.dropdown-content` |
| 移动端 | 右上角紧凑浮层 `fixed right-4 max-h-[80vh]` + 手风琴 | 全屏 MD3 抽屉（遮罩 + 340px 侧滑 + 标题栏） |
| 键盘/滚动 | 与本地一致 | 与参考站一致 |

**结论**：结构差异是纯 `navBarConfig.ts` 数据层的事，无需改组件；组件层真正值得对齐的是下拉显隐过渡的"单一容器"写法。另发现一个**继承自参考站的潜在 bug**（见 Phase 2）。

---

## Phase 1 · 导航数据扁平化（`src/config/navBarConfig.ts`）

把 `getDynamicNavBarConfig()` 从"5 个分组下拉"改为参考站的"常用项直链 + 必要分组"：

```
主页(直链) → 归档(直链) → 分类(直链) → 标签(直链) → 系列(直链)
  → 社交▾{友链, 留言}
  → 我的▾{动态, 项目, 相册, 书签导航, 哔哩哔哩, 番组计划, VNDB, AnimeList}
  → 关于▾{打赏, 关于我}
  → 链接▾{GitHub, Gitee, Firefly文档}
```

- 保留 `LinkPresets` 不动（名称/图标/URL/pageKey 全部复用）。
- "文章"组拆开为 4 条直链（参考站的 归档/专题 就是直链形态）；`社交/我的/关于/链接` 仍是分组。
- 分组内只有 1 个子项时，`resolveNavMenuLinks()` 已有的**自动塌缩为直链**逻辑会自动生效，无需额外处理。
- 无新增类型、无新增 i18n key（沿用 `NAVBAR_DEFAULT_NAMES` 现有映射）。

> 说明：我**不会**照搬参考站的 `专题 /hubs/`、`周刊 /weekly/` —— 那是该站专属页面，本仓库没有对应路由。

## Phase 2 · 下拉显隐对齐（`src/styles/main.css` + `DropdownMenu.astro`）

参考站的写法是**所有过渡状态集中在 `.dropdown-menu` 一个容器上**，本地则拆成 `.dropdown-menu`(pointer-events) + `.dropdown-content`(opacity/translate) 两层。对齐为单一容器：

```css
.dropdown-menu {
  @apply absolute top-full left-0 pt-2 z-50
         invisible opacity-0 translate-y-[-8px] pointer-events-none
         transition-[opacity,visibility,translate] duration-200 ease-out;
}
.dropdown-container:hover .dropdown-menu,
.dropdown-container:focus-within .dropdown-menu {
  @apply visible opacity-100 translate-y-0 pointer-events-auto;
}
```

- 删除 `.dropdown-content` 上的 `opacity-0 translate-y-[-8px]` 与对应 hover 规则（保留其卡片底色/圆角/阴影/`min-w-48`）。
- 好处：闭合时真正 `visibility:hidden`（当前只挡了 pointer-events，闭合菜单仍可被读屏/焦点命中），且移除了 `.dropdown-container:focus-within .dropdown-menu` 的重复声明。
- 风险低：纯 CSS，Astro scoped 样式不影响其它组件。

**顺带修一个继承自参考站的 bug**：桌面菜单在 `lg`(1024px) 隐藏、汉堡按钮 `<1024px` 显示，但 `.dropdown-container` 的隐藏断点写的是 `max-width: 768px`（`main.css:520`、`DropdownMenu.astro:95`），导致 **768–1023px 区间汉堡与桌面下拉同时出现**。统一改为 `max-width: 1023px`。

## Phase 3 · 移动端形态：保持现状（推荐）

参考站的紧凑浮层在**功能上弱于**本地全屏抽屉（无遮罩、无滚动锁定 `data-floating-panel-scroll-lock`、无 `role="dialog"`、无 Escape 焦点回归），本地的 `NavMenuPanel` 已接入 `floating-panel-utils` 的 `inert`/aria/滚动锁体系。**建议保留本地抽屉**，仅确保其在 Phase 1 的扁平数据下正常渲染（`markActiveNav` 的父级自动展开对手风琴仍适用）。

若你确实想要参考站的紧凑浮层外观，我可以改为"复用现有抽屉逻辑、只换 CSS 皮肤"的方案——但这会丢掉遮罩/滚动锁体验，所以我默认不做。

## Phase 4 · 验证

1. `pnpm check` + `pnpm type-check`
2. `pnpm dev`，检查：
   - 桌面 ≥1024px：直链点击、分组下拉 hover/focus 展开、键盘 ↑↓/Esc/Enter
   - 768–1023px：确认汉堡出现时桌面下拉不再重复渲染（Phase 2 修复）
   - 移动端抽屉：扁平化后手风琴收起、当前页高亮仍正确
3. `pnpm build` 确认无回归
